# AWS LiveKit staging preparation

Status: staging configuration generated locally; no AWS LiveKit resources created and no app traffic moved.

## Scope

- Schedora web/API moves to ECS Fargate; LiveKit runs separately on an EC2 VM for WebRTC UDP and host networking.
- Keep Supabase Postgres and its connection unchanged.
- Keep the existing Render and LiveKit Cloud production services until AWS staging passes and the production cutover is separately reviewed.

This is a staging starting point, not a high-availability or production capacity design. A single EC2 node has no failover, and its performance and media bandwidth must be load-tested before production. The full app migration plan is in `docs/AWS_DEPLOYMENT.md`.

## Files prepared

- `infra/aws/livekit-staging.yaml` provisions one Ubuntu EC2 instance, encrypted 30 GB gp3 disk, Elastic IP, a media-only security group, and Systems Manager access. It opens no SSH port.
- `infra/aws/schedora-ecr.yaml` and `infra/aws/schedora-web.yaml` prepare the separate application path to ECR and ECS Fargate.
- The EC2 User Data is generated by LiveKit's official VM generator for `lk-stage.schedora.in` and `turn-stage.schedora.in`, pinned to LiveKit Server `v1.13.11`, bundled Redis, and Ubuntu cloud-init. Generated files live under the git-ignored `infra/aws/livekit-staging/generated/` directory and include staging-only API credentials; do not commit or paste them into chat.

## Required before creating the stack

1. The official `livekit/generate` container has run and generated the Ubuntu cloud-init and service configuration for `lk-stage.schedora.in` and `turn-stage.schedora.in`. Keep these hostnames and credentials staging-only.
2. After the EC2 stack exists, add DNS A records for both names to the stack's Elastic IP. Do not point them at the Meet application load balancer.
3. In the AWS console, select Mumbai and an existing VPC public subnet with an Internet Gateway route. The generated EC2 instance needs outbound internet for package downloads and automatic TLS certificates.
4. The GitHub OIDC deployment role and scoped policy exist. Use that role for the workflow; do not use the AWS root user. The workflow files have not been pushed and no LiveKit EC2 stack has been created.
5. Confirm the estimated ongoing EC2, public IPv4/Elastic IP, and outbound data-transfer charges in AWS Pricing Calculator. Video egress can dominate the bill; the instance type in the template is only a staging default.

## Staging sequence

1. Run LiveKit's official generator locally for the two staging DNS names. Do not enable recording, egress, ingress, SIP, agents, or other optional paid features.
2. Keep the generated files outside version control. Use staging-only LiveKit API credentials; the generated cloud-init contains deployment configuration and may contain secrets.
3. Review the generated `livekit.yaml` before launch: set `room.auto_create: false`, constrain participants and room duration, and confirm webhook configuration targets the Schedora staging webhook. Keep token TTL at or below 120 seconds until the self-hosted revocation review is complete.
4. Deploy `infra/aws/livekit-staging.yaml` through CloudFormation with the selected VPC/subnet, staging instance size, and the generated cloud-init encoded as User Data. Review the change set before execution. The User Data value is retrievable by AWS administrators from EC2 metadata APIs, so use staging-only credentials and rotate them after the test.
5. Add DNS A records for both names to the stack's Elastic IP. Wait for propagation and verify Caddy obtains trusted TLS certificates.
6. Use Systems Manager Session Manager to check the generated `livekit-docker` service, health/logs, firewall, and metrics. Verify camera, microphone, screen share, two-browser join, remove participant, end-room, webhook delivery, usage settlement, and reconnect behavior.
7. Do not edit the production Render variables until staging evidence passes and the production security review confirms self-hosted token revocation/room recreation behavior. Keep the existing LiveKit Cloud deployment available for rollback and room draining.
8. When staging is no longer needed, delete the CloudFormation stack to release the EC2 instance and Elastic IP.

## Deployment gates still open

- GitHub identity verification is required before the updated Meet certificate ARN variable can be saved.
- The runtime boundary now allows the exact AppBeta secret ARN in addition to the `schedora-*` pattern. AWS confirmed the update; the secret values were not inspected.
- The local GitHub Actions workflow includes a manual LiveKit staging deployment. It still needs the generated cloud-init stored as an encrypted Actions secret before that job can run.
- The generated LiveKit API credentials must be placed in the app's staging secret without exposing them in chat, and the app must be configured to use the self-hosted staging endpoint before video can be enabled.
- A staging DNS zone and public subnet must be selected for LiveKit.
- The staging webhook endpoint must be reachable from LiveKit; the current local runner is not a durable public staging endpoint.
- Cost and region capacity need confirmation in the AWS account.
- No LiveKit VM, video smoke test, load test, security review, production variable change, or production cutover has been completed.

The generated output directory is excluded from Git and Docker build contexts so its configuration cannot be committed accidentally or copied into the Schedora app image.
